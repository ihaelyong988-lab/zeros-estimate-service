## 1. 왜 매주 새 오류가 나왔는가 (근본 원인)

**자동 검출 장치가 0이었다.** 테스트도 CI도 `npm test` 스크립트조차 없었다.
결함을 찾는 유일한 수단이 "사람이나 AI가 15,000줄을 손으로 훑는 것"이었고, 손으로 전수를 잡는 것은 불가능하므로 **조사할 때마다 새로 나왔다.**

이건 작업자의 문제가 아니라 구조의 문제였다. 조사를 반복하는 한 이 사이클은 끝나지 않는다.

**처방**: 조사를 그만두고 그물을 깐다. 결정적 관찰은 **돈 버그 7건이 전부 순수 함수 3개 파일에 있었다**는 것이다(`lib/calculations.ts`·`lib/quote/quoteDraft.ts`·`lib/quote/quoteXlsx.ts`). UI·브라우저·DB가 필요 없어 테스트가 싸고 빠르다.

이 처방은 `AGENTS.md §14`로 명문화됐다.

- **§14-1 테스트 우선** — 새 결함은 실패하는 테스트로 먼저 고정한 뒤 고친다.
- **§14-2 보호 목록** — `lib/quote/*`·`lib/calculations.ts`·`lib/payments/*`·`lib/crm/*`는 **주간 전수 조사 대상에서 제외**한다. 회귀는 `npm test`가 잡는다.
- **§14-3 CI 통과 필수** — master 푸시 = 자동 배포이므로 CI 실패는 곧 배포 사고다.
- **§14-4 금액 단위 불변식** — `estimated_amount`는 공급가액(VAT 별도). 읽기는 `supplyAmountOf()`로만.

## 2. 단계별 결과

### 1단계 (7/31) — 안전망 + 돈 정합성 + 거짓정보

**돈**: 견적서를 다시 만들 때마다 금액이 10%씩 불어나던 것(4,000만 → 4,416만 → 4,836만), 미수금이 계약금 전액으로 잡히던 것(3억 수주 + 수수료 30만 미결제 = 미수금 3억), 매출이 수주월이 아니라 접수월에 꽂히던 것, 결제가 중복으로 쌓이던 것, 견적을 지워도 고객 누적치가 안 줄던 것.

**거짓정보**: AI 도면 스캔이 도면과 무관하게 **고정 3,850만원**을 고객 견적서에 넣던 것(기능째 제거), 알림이 한 통도 안 나가면서 전부 '발송 성공'으로 찍히던 것, 인쇄물의 미치환 변수·근거 없는 보증 문구, 한 화면에 97.8%와 99.x%가 동시에 보이던 신뢰 지표.

**안전망이 즉시 값을 했다** — 깔자마자 실제 버그 2건을 잡았다. 평균 소요일이 오염 데이터에서 −10일로 나오던 것과, **고객 견적서에 인건비 단가가 450,000원이 아니라 300,000원으로 찍히던 것**(기준액 111만~227만 구간, 스윕 1,409건). 후자는 화면만 봐서는 절대 알 수 없다.

### 2단계 (8/1) — 방문자 이탈 차단

**가장 중요했던 것**: 인증 토큰이 서버로 전송되는 경로가 **아예 없었다.** `PhoneVerifyGate`가 `verifiedToken`을 만들어 넘기는데 `RequestWizard`가 구조분해에서 그것만 빼고 받아 버렸다. 서버는 그 토큰을 요구한다. **문자키를 등록하는 순간 모든 접수가 403으로 실패할 상태였다.**

그 외: 모바일 주 CTA가 도면 첨부칸 없는 채널로 직행하던 것, 마이페이지가 조회 실패를 "접수 내역 없음"이라 거짓 안내하던 것, 무엇을 신청하는지 보기도 전에 인증이 막던 것, 모바일 로그인 버튼이 죽어 있던 것.

### 3단계 (8/1) — 체감·구조

번들 분리(고객이 관리자 백오피스 1MB를 내려받던 것), SSR 경량판(서버 HTML 본문의 실질 단어가 'ZEROS' 하나였다), 접수목록 페이지네이션, 관리자 탭 캐시, 이미지 최적화.

## 3. 판단 근거 기록 — 왜 그렇게 정했는가

같은 고민을 다시 하지 않기 위해 남긴다.

| 사안 | 결정 | 근거 |
|---|---|---|
| 미수금 정의 | **Payment 행(청구−수납) 기준** | 기존 정의가 명백히 틀렸다. 판정 기준이 계약금이 아니라 출장견적비(수만원) 결제 여부였다. 대시보드 숫자가 억 단위 → 수십만원대로 급감하지만 **이전 값이 오탐**이었다 |
| 견적 초안 잔차 | **정산해 합계를 기준액과 일치** | 4,000만 기준에 40,150,000이 나오던 것을 정확히 맞춘다. 단 **공수(인건비) 행은 정산 대상에서 제외** — 표준 노임단가가 견적 근거라 차액을 흡수시키면 근거 없는 단가가 찍힌다 |
| VAT 저장 여부 | **저장하지 않고 파생** | 공급가액에서 총액은 무손실 역산되므로 필드를 늘릴 이유가 없다. 두 값을 저장하면 어긋날 경로가 생긴다(헌법 제10조 1정보 1표시) |
| 기존 오염 데이터 | **마이그레이션 없이 자동 정규화** | 저장값이 품목 합계의 정확한 VAT 포함액이면 오염으로 판정해 공급가액을 반환한다. DB 손대지 않는다 |
| 고객 등급 백필 | **백필 없이 폴백** | 기존 `customer_grade`가 수동 지정값이면 그대로 읽어 화면 표시를 보존한다. SQL 실행 불필요 |
| CRM 누적치 | **저장 카운터 → 견적 파생 계산** | 카운터 방식은 삭제·정정을 따라가지 못한다. 파생이 근본 해결 |
| 사업소개 CTA 문구 | **변경 안 함(보류)** | `AGENTS §10`에 문자열째 확정된 조문. 조문 개정 없이 건드리면 규칙 위반. 본문과 모순되는 문제는 남아 있으나 별도 판단 사항 |
| 예산 옵션 저장값 | **불변, 라벨만 교정** | `ExpectedBudgetRange`는 DB 저장 키이자 `quoteDraft.baseAmount` switch 분기 기준. 바꾸면 기존 데이터와 갈라진다 |
| SSR 전면 재설계 | **하지 않음. 경량판만** | 부팅 구조(`layoutReady` 게이트)를 건드리면 픽셀 게이트가 깨진다. 스플래시 본문화 + `noscript` + 메타만으로 손실 대부분을 회수 |
| OTP fail-closed 강제 | **넣지 않음** | 문자키 미설정 상태에서 강제하면 접수까지 막힌다. 키 등록 후 켜는 구조 |

## 4. 이 작업에서 배운 것 (재발 방지)

### ① 로컬 빌드 성공이 배포 성공을 보장하지 않는다

1단계 커밋에서 `git add -u`(추적 파일만)를 쓰고 신규 파일을 손으로 나열하다 **`lib/constants/trust.ts`를 빠뜨렸다.** master의 코드는 그 파일을 import하므로 **클린 체크아웃 빌드가 실패하는 상태**였다. 로컬이 계속 통과한 것은 파일이 디스크에만 있었기 때문이다.

**처방**: 커밋 전 `git status --porcelain | grep '^??'`로 미추적 소스 잔여를 확인한다. 배포 후에는 **GitHub에서 새로 클론해 `npm ci → tsc → test → build`**를 돌려 검증한다. 2단계부터 이 절차를 적용했다.

### ② 적대적 검증은 건너뛰면 안 된다

이번 작업에서 검증이 배포 직전에 막아낸 것들이다. 전부 실행했으면 사고였다.

- 무인 자동 배포가 라이브 로그인·접수를 중단시킬 뻔한 계획(1단계 착수 전)
- 관리자 토큰이 남은 브라우저에서 공개 홈·실적이 통째로 비는 회귀(7/30)
- 고객 견적서에 근거 없는 인건비 단가가 찍히던 결함(1단계)
- 클린 빌드가 깨져 있던 상태(2단계)
- `/api/otp/status` 캐시로 키 등록 후 인증이 어긋나던 문제(2단계)

**검증자는 "이건 틀렸다"를 기본 입장으로 두고, 숫자 주장은 직접 재계산하게 해야 한다.** 스윕 테스트로 1,409건을 찾아낸 사례가 그 값을 보여준다.

### ③ 파일 배타 소유를 지키지 않으면 변경이 조용히 사라진다

병렬 기수가 같은 파일을 만지면 나중에 쓴 쪽이 앞엣것을 덮어쓴다. 계획 단계에서 **파일 충돌 지도**를 먼저 그리고, 겹치면 한 기수로 합쳤다(2단계에서 6기 → 5기, 3단계에서 5건 → 4기).

### ④ 확정 조문과 충돌하면 실행하지 말고 보고한다

홈 히어로 폰트 16px 상향은 §10 본문 규칙에는 맞지만 O-37 세로 예산과 모순이었다(루트가 `overflow-hidden`이라 스크롤이 아니라 **클리핑**된다). 어느 방향으로 가도 조문 위반이라 판정 보류로 남겼다.

## 5. 남은 것

### ★ 잔여작업 1 — Vercel env 4종 등록 (다음 차수 예정)

**상태: 미착수.** 절차 전문은 `docs/03_qa_deploy/prod-env-setup.md`(2026-08-01 현행 상태 반영됨).

**실측한 현재 상태(2026-08-01)**

| 키 | `.env.local` | 필요한 일 |
|---|---|---|
| `SOLAPI_API_KEY` | 비어있음 | Solapi 발급 |
| `SOLAPI_API_SECRET` | 비어있음 | Solapi 발급 |
| `SOLAPI_SENDER` | 비어있음 | 발신번호 등록·심사 **1~2일 소요** |
| `ZEROS_ADMIN_PASSWORD` | 비어있음 | 주인님이 정하면 됨 |
| `OTP_SERVER_SECRET` | 설정됨(64자) | Vercel 등록 여부 미확인 |
| `SUPABASE_SERVICE_ROLE_KEY` | 설정됨(41자) | 완료 |

`vercel` CLI는 설치돼 있으나 **프로젝트 미연결**(`.vercel/project.json` 없음).

**순서**

1. **Solapi 가입 → 발신번호 등록(통신서류 심사 1~2일) → API Key/Secret 발급.** 이 단계가 시간을 잡아먹는다. 발신번호는 명의 확인된 번호여야 한다.
2. `.env.local`의 빈 4칸을 채운다. `SOLAPI_SENDER`는 하이픈 없이 숫자만.
3. 최초 1회: `npx vercel login`(브라우저 인증) → `npx vercel link`(프로젝트 `zeros-estimate-service` 선택).
4. `./scripts/push-env-vercel.ps1` 실행 — `.env.local`을 읽어 Vercel로 직접 전송한다(**값이 AI·채팅을 거치지 않는다**).
5. AI에게 "재배포하고 검증해" — 빈 커밋 푸시로 재배포 + `node scripts/prod-probe.mjs` 3/3 PASS 확인.

**선행 조건은 이미 해소됐다.** 2단계(P2-2)에서 `verifiedToken` 전송 경로를 만들었으므로 **키를 등록해도 접수가 막히지 않는다.** 그 전에 등록했다면 모든 의뢰 접수가 403으로 실패했을 것이다.

**등록 후 달라지는 것**: 문자 인증 실작동(마이페이지 로그인이 풀린다) · 관리자 로그인 가능(현재 503).

**미리 알 것**: 문자 발송은 건당 과금이라 Solapi 충전이 필요하다. 남용 완화는 코드에 이미 있다(번호당 1시간 5회·IP당 20회, `lib/otp/rateLimit.ts`).

**급하지 않다.** 지금도 접수는 작동한다(인증 게이트 생략 상태). 다만 그동안은 **아무나 남의 번호로 접수할 수 있다**.

### ★ 잔여작업 2 — 알림 실제 발송 경로 (다음 차수 예정)

**상태: 미착수. 위 env 등록을 마쳐도 이 문제는 남는다.**

전수 grep 결과 `sendSms`(`lib/sms/send.ts`) 호출부는 **`app/api/otp/send/route.ts` 한 곳뿐**이다. 이건 본인인증 코드 발송 전용이고, 상태 알림(`zeros_notification_logs`)을 만드는 경로에는 **발송 호출 자체가 없다.**

→ "견적서 송부완료" 같은 상태 알림은 이력만 쌓이고 고객에게 아무것도 가지 않는다. 1단계에서 이력 표기를 **'미발송'**으로 정직하게 바꿔 뒀다(전에는 전부 '발송 성공'으로 찍혔다).

**필요한 일**: 서버 발송 경로 구축. 알림 생성이 브라우저 `lib/supabase/client.ts`에서 일어나는데 SMS 발송은 서버에서만 가능하므로, `/api/data`의 알림 생성 지점이나 별도 서버 라우트에서 `sendSms`를 부르는 구조가 필요하다. 발송 실패 시 이력 status를 정확히 남기는 것까지 포함.

### 코드로 남은 것

- **알림 실제 발송 경로** — 문자키를 등록해도 상태 알림은 나가지 않는다. `sendSms` 호출부가 본인인증 1곳뿐이고 알림 생성 경로에는 발송 호출 자체가 없다. 서버 발송 경로 구축이 필요하다.
- **중복 결제 행 정리** — 이미 쌓인 것. 판별 기준은 1단계 일지에 기록돼 있다.
- **`line_items` 없는 구 데이터** — VAT 포함 금액이 품목표 없이 저장된 행은 정규화 수단이 없다. 라이브에서 해당 행 수를 세어 볼 것.
- **확정매출 정의 이원화** — `calculations.ts`는 `confirmed_contract_amount`만, `customerRollup.ts`는 폴백을 쓴다. 정상 경로는 값이 같지만 통일 필요.
- **Mock 경로 CRM 파생 부재** — 파생이 `/api/data`에만 있어 로컬 Mock 실행 시 누적치가 안 바뀐다(라이브 무관).
- **판정 보류 항목** — 홈 폰트 조문 모순 · 홈 데스크톱 푸터(O-32와 충돌) · 홈 5색 카테고리 팔레트 · 로고 그라데이션 · 명칭 3종 혼재('무료 견적 신청/의뢰/검토 신청').

### 다음 주부터의 작업 방식

`AGENTS §14-2`에 따라 **보호 목록 모듈은 조사하지 않는다.** 조사 범위는 보호되지 않은 영역(컴포넌트·API 라우트·미검증 유틸)으로 좁힌다.
새 결함을 발견하면 §14-1대로 **실패 테스트를 먼저 쓰고** 고친다. 그러면 같은 결함이 구조적으로 재발할 수 없다.
