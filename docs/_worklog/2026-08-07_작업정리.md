## 3. 적대 검증이 잡은 것 — 배포 전 봉합 4건

**이 값이 이번 차수의 핵심이다. 네 건 다 그대로 나갔으면 사고였다.**

| # | 검증관이 반증한 내용 | 봉합 |
|---|---|---|
| 1 | **A2가 봉합되지 않았다.** 검증은 `file_path`만 하는데 저장은 클라이언트 `FileMeta`를 통째로 한다. `/api/files/sign`의 `customerOwnsPath`는 `file_url`도 읽으므로, 검사받지 않은 `file_url`에 남의 경로를 실으면 서명 URL이 그대로 발급된다 | 알려진 필드만 재구성 + `file_url` 강제 공란 |
| 2 | **번호 레이트리밋이 정상 고객을 차단한다.** 검증보다 앞이라 400을 받은 요청도 한도를 소모 — 세 번 실수하면 1시간 접수 불가. OTP가 생략되는 현 환경에선 제3자가 남의 번호를 봉쇄할 수 있다 | 번호 버킷을 전 검증 통과 후로 이동(IP 버킷은 전량 스캔 보호용이라 앞에 유지) |
| 3 | **B1이 만든 회귀.** STEP1이 796px → 1,299px가 되면서 오류 배너가 뷰포트 밖(top −370px)에 렌더 → 고객에게 '다음' 무반응 화면 | 배너에 `ref`+`tabIndex`, 오류 발생 횟수를 신호로 `scrollIntoView`+`focus`. 같은 문구를 버튼 옆에 복제하는 방식은 헌법 제10조 위반이라 쓰지 않았다 |
| 4 | **C1이 만든 회귀.** 죽은 `<span>`이 링크가 되면서 93×20px 터치 타깃 발생(§10 ≥44px 위반) | 세로 여백만 확장해 44px 확보. O-32가 확정한 것은 구성·문구·순서·테두리·폭이고 히트 영역은 규정하지 않으므로 조문 충돌 아님 |

1·2는 서버 보안, 3·4는 이번 변경이 만든 회귀다. **1·2는 A단계 기수가 "완료"로 보고한 항목이었다** — 보고를 믿지 않고 코드를 직접 읽게 한 것이 값을 했다.

## 5. 이번 차수에 새로 발견된 것 (다음 차수)

작업 중 부수적으로 확인된 것들. 결함대장 부록 B에 등재했다.

- `CustomerList.handleSaveClick` 저장 실패가 `console.error`만 하고 화면엔 성공처럼 보인다
- `VisitList.handleCompleteVisit`의 `alert('상태 변경 실패')`가 원인을 알리지 않는다

- STEP1 공사 종류 `radiogroup`의 tab stop이 18개다 — ARIA APG는 roving tabindex로 1개를 기대한다
- 같은 값의 두 표기: 접수 칩은 `menuDisplayName`('일반 배관공사'), 마이페이지·관리자는 원시 `work_type`('배관공사')
- 결제 행 **삭제** 경로 부재(`/api/data`에 `deletePayment` op 없음)
