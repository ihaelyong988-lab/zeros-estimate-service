## 1. P2-2. 문자키를 등록하면 모든 접수가 실패하던 문제 (최우선)

**착수 전 실측한 상태**:
- `PhoneVerifyGate.tsx:66`이 인증 성공 시 `verifiedToken`을 넘긴다.
- `RequestWizard.tsx:210`의 `handleVerified`가 `{ name, phone, sessionToken }`만 구조분해해 **토큰을 그냥 버린다.**
- `lib/supabase/client.ts`의 `authBody()`는 `adminToken`·`sessionToken`·`phone`만 싣는다 — **`verifiedToken` 전송 경로가 코드에 존재하지 않았다.**
- 서버 `app/api/data/route.ts:224`는 `verifiedToken` 또는 유효한 `sessionToken`을 요구한다.

즉 **토큰을 만들어서 버리고 있었다.** 지금은 문자키가 없어 인증 게이트 자체가 생략되니 드러나지 않을 뿐, 키를 등록하는 순간 주소·연락처·도면을 다 넣은 마지막 단계에서 403이 뜨고 재인증 경로도 없어 그대로 이탈했을 것이다.

**조치**:
- 토큰 판정을 **순수 함수로 분리**했다 — `pickEstimateAuth(phone, record, session, now)`. 번호가 다르거나 만료가 뻔한 토큰은 실어 보내지 않는다. 인증 완료 표시도 같은 판정을 쓴다("화면은 인증됨, 서버는 미인증" 어긋남 차단).
- `handleVerified`가 `verifiedToken`을 보관하고, `createEstimate` 호출에 `{ visit, verifiedToken }`로 실어 보낸다. 서비스 인터페이스·Base·Supabase 구현 3곳을 맞췄다.
- `DataRequestError`로 **상태코드를 보존**해, 403/401이면 인증 화면을 다시 열어 복구 경로를 준다.
- 접수 실패 시 **서버가 준 사유를 그대로** 보여준다(기존엔 "다시 시도해 주세요"만 반복).
- `logoutCustomer`가 sessionStorage 인증 흔적도 폐기한다(같은 탭에서 로그아웃 후 재의뢰 시 게이트가 안 뜨던 문제).

**체인 확인(코드 추적)**: `PhoneVerifyGate:69` → `RequestWizard:212` 보관 → `RequestWizard:459` 전달 → `client.ts:700` 서버 body → 실패 시 `RequestWizard:471` 인증 화면 재개.

**현재 동작 보존**: 문자키 미설정 상태에서는 지금처럼 접수가 되어야 한다는 제약을 걸었다.

## 2. P2-1. 모바일 주 CTA가 도면 못 올리는 채널로 직행하던 문제

**착수 전 실측**: `app/page.tsx:1480`(히어로 하단)·`1674`(3페이지 최종)가 `openRequestChannel('quick')`으로 채널 선택 화면을 건너뛰었다. 그런데 `RequestWizard.tsx:835`의 자료 첨부 블록은 `{channel === 'visit' && (`로 감싸여 있어 **quick 폼에는 도면 업로드 칸이 아예 없다**(주석도 "출장요청(visit) 채널만"이라 명시).

3페이지에서 2.2억 슬라이더를 보고 그 아래 버튼을 누른 사람이 조건도 모른 채 소액 건으로, **도면 없이** 접수됐다. 도면 없는 건은 운영자도 견적을 낼 수 없다.

**조치(확정안)**: 두 CTA를 **채널 선택 화면으로** 보낸다. 방문자가 두 채널을 나란히 보고 고른다. 히어로 상단 링크칩의 visit 직행은 이미 도면 첨부가 열리는 경로라 그대로 뒀다.

## 3. P2-3. 마이페이지가 조회 실패를 "접수 내역 없음"이라 거짓 안내하던 문제

**착수 전 실측**: 세션 만료 시 견적은 200(허용목록 행 → phone 필터에서 0건), 알림은 401이 난다. 둘이 `Promise.all`로 묶여 **401 하나에 전체가 catch로 빠지는데**, catch는 콘솔에만 찍고 화면은 정상 렌더되어 "접수된 사전진단 내역이 없습니다"를 확정형으로 띄웠다. 도면 올리고 의뢰까지 끝낸 고객 눈에 **접수 건이 통째로 사라진 것처럼** 보였다.

**조치**:
- `Promise.allSettled`로 전환 + 판정 로직을 **순수 함수로 분리**(`resolveRequestsLoad`). 견적은 성공하고 알림만 401이면 **견적 목록은 정상 표시하고 오류 배너만** 얹는다.
- 오류 상태를 "0건"과 분리해 보관한다. 배너에 `role="alert"`를 달고 **"다시 시도"**, 세션 만료면 **"다시 인증하기"** 버튼을 준다.
- 진짜 0건일 때만 기존 빈 상태 문구를 유지한다.
- `MyRequestsView`·`MyRequestsModal` **양쪽 모두** 고쳤다(한쪽만 고치면 페이지와 모달이 다르게 동작).

## 9. 적대 검증이 잡은 것 — 배포 차단 결함 1건 포함

### ⚠ 배포 차단: 1단계 커밋에서 신규 파일 4개가 누락돼 있었다

**가장 중요한 발견이다.** 1단계 커밋 때 `git add -u`(추적 파일만 스테이징)를 쓰고 신규 파일을 손으로 나열했는데, **`lib/constants/trust.ts`를 빠뜨렸다.**

그런데 `origin/master`의 `app/page.tsx:8`과 `components/layout/RightSidebar.tsx:8`이 이 파일을 import한다.
→ **클린 체크아웃에서 `Module not found: @/lib/constants/trust`로 빌드가 실패한다.**

로컬 빌드가 계속 통과한 이유는 파일이 **내 디스크에만 존재**했기 때문이다. 로컬 성공이 배포 성공을 보장하지 않는다는 것을 보여주는 사례다.

**조치**: 누락 4개 파일을 전부 스테이징했다 — `lib/constants/trust.ts` · `lib/requests/loadOutcome.ts` · `test/requests/loadOutcome.test.ts` · `test/supabase/estimateAuth.test.ts`. 인덱스 존재를 `git cat-file -e`로 기계 확인했고, `git status`로 미추적 소스 0건을 확인했다.

**재발 방지**: 커밋 전 `git status --porcelain | grep '^??'`로 미추적 소스가 남았는지 확인한다. `git add -u`만으로는 신규 파일이 절대 들어가지 않는다.

### 그 외 필수 수정 3건

- **`/api/otp/status` 캐시**: 응답에 `Cache-Control`이 없어 브라우저가 무기한 캐시한다. 실측에서 curl은 `{enabled:false}`인데 브라우저는 `{enabled:true}`를 3회 연속 캐시에서 반환했다. 문자키 등록 직후 화면과 서버 상태가 어긋나 인증을 끝내지 못하는 사용자가 생긴다 → `no-store, must-revalidate` 추가.
- **모바일 마이페이지 로그인 폼 중복**: P2-5가 모달을 항상 마운트하게 만들면서, 마이페이지 탭에서는 인라인 로그인 폼과 모달이 겹쳐 '인증번호 전송'이 2회 렌더됐다(헌법 제10조 1정보 1표시 위반) → 마이페이지 탭에서는 헤더 로그인 버튼을 숨긴다.
- **성함 라벨 불일치**: STEP2 라벨은 `담당자 성함 (선택)`인데 인증 게이트는 성함을 필수로 막는다 → `(선택)` 표기를 제거해 실제 동작과 일치시켰다.
